The main host hotspot is jax_array_from_reshaped_torch: 127.972 s TP8 / 127.584 s TP16 across 1188 conversions. The slowest boundaries are attention o_proj weights; representative TP8 rank zero has layers 29/5/53/11 taking about 4.0 s exclusive conversion each (raw top20 in the deploy evidence). [INFERENCE] Their reshape/permutation misses t2j's contiguous-bfloat16 fast bitcast and takes the torchax fallback. This specific inner conversion cause was not separately timed. There are 3365 compile_or_get_cached calls and 333 clear_caches calls in BOTH layouts. Source weight_utils.py:1070-1073 clears caches after each module's post-load processing, so [INFERENCE] repeated cache clearing removes in-process reuse of shape-compatible load kernels; the profile alone does not prove that counterfactual speedup.

Halving per-host/per-chip final bytes does not halve load: load time is essentially unchanged, while raw transfer drops from 2.647 to 1.636 s. This rules out final per-chip transfer bytes as the dominant cost. Full checkpoint size and tensor count are held fixed, so these two deployments cannot distinguish full-host-byte scaling from tensor-count scaling. Costs are not uniform per tensor: a few o_proj conversions are much slower than the 1188-tensor average.

[ESTIMATE] A pre-sharded snapshot containing final dtype/layout arrays skips the full-tensor host conversion, merge/reorder/local shard selection, and most load-kernel compile/cache activity; it still needs snapshot reads, array/model reconstruction and TPU transfer. The observed transfer-only load floor using these measured final-shard puts is 2.65 s TP8 / 1.64 s TP16 per worker, excluding those remaining costs. This is not achieved restore latency or a hardware-spec-sheet estimate; bandwidth is measured at synchronized raw batched_device_put, with 1031 calls per worker (1028 weight puts plus tiny initialization arrays).
